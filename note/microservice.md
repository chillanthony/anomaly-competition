# 微服务架构 & 赛题系统架构名词解释

## 一、微服务架构（简述）

**一句话：** 把一个大系统拆成一组各自独立运行、通过网络互相调用的小程序，每个小程序只干一件事，可以单独开发、单独部署、单独扩容、单独挂掉。

### 从单体到微服务

| | 单体（Monolith） | 微服务（Microservices） |
| --- | --- | --- |
| 部署形态 | 一个进程，一个包 | 几十上百个进程，各跑各的 |
| 改一处 | 整个系统重新发版 | 只重发那一个服务 |
| 扩容 | 整机复制 | 只扩瓶颈服务 |
| 故障影响 | 一处崩，全站崩 | 单服务崩，其余可降级 |
| 调用方式 | 函数调用（内存内，纳秒级） | 网络调用（RPC/HTTP，毫秒级，且可能失败） |
| 数据 | 一个库，事务简单 | 每个服务自己的库，分布式事务麻烦 |

核心动机是**降低耦合**：让团队规模、发版节奏、扩容粒度都能按服务切开，而不是被一个巨大的代码库绑死。

### 代价（这才是和本赛题相关的部分）

拆开之后，原本"函数调用"变成了"跨网络调用"，于是凭空多出一堆新问题：

- **服务发现**：A 要调 B，B 有 10 个实例、IP 还会变，怎么找到它？ → 注册中心（Consul / Nacos / K8s Service）
- **负载均衡**：请求分给哪个实例？
- **熔断降级**：B 挂了，A 不能跟着一起挂 → 熔断器（Hystrix / Sentinel）
- **链路追踪**：一次请求穿过 8 个服务，哪一段慢？哪一段报错？ → Trace / Span / OpenTelemetry
- **可观测性**：服务多了，人肉看日志不现实 → 三大支柱 **Metrics（指标）、Logging（日志）、Tracing（链路）**，统称 **可观测性（Observability）**
- **故障传播**：网络延迟、实例资源耗尽、依赖服务雪崩，异常会在服务之间"传染"

**为什么赛题提这个：** 赛题环境里的 `service-vm-1/2/3` 就是三个微服务实例，它们之间以及和 `traffic-vm` 之间是网络调用关系。"服务级故障"就是某个服务实例本身出问题（进程挂了、响应变慢、返回错误），它表现出的异常和"链路级""路由级"故障会**互相混淆**——同样是访问超时，可能是链路延迟、可能是路由绕行、也可能是服务自己卡住了。所以赛事方要求你同时用 Metrics、Logs、NetFlow 三类数据交叉验证。

> 赛事方明确"鼓励采用多智能体架构（Multi-Agent System）"——注意区分：**微服务**是"把业务拆成多个服务"的架构风格，**多智能体**是"用多个 LLM Agent 分工协作"的解题方法，两者不是一个层面的东西，别混。

## 二、系统架构这段话，逐词翻译

### 1. 区域（region）：把大网切成 8 块

- **核心区域（3 个）**：北大、武汉、上海 —— 相当于省会级骨干节点，承载主要业务，跨区流量大多要经过它们。
- **边缘接入区域（5 个）**：沈阳、西安、南京、成都、广州 —— 相当于地市级接入点，业务量小，主要往外连。

### 2. "非全互联"：不是两两直连

- **全互联（full mesh）**：8 个区域两两之间都拉一根线，共 $\binom{8}{2}=28$ 条链路。简单、路径最短，但成本高、不可扩展。
- **非全互联（partial mesh）**：只连一部分链路（比如边缘只连到最近的核心）。省成本、更像真实运营商网络，但**去一个地方可能要绕路**。

这就直接产生了后面两个词：

- **多跳（multi-hop）**：数据从 A 到 B 中间要经过好几个路由器/区域，不是一跳直达。
- **路径绕行（rerouting）**：主路径断了，路由协议自动换一条更长的路走。**这就是本题的关键难点**——绕行之后，异常会出现在"新路径"的网元上，而不是真正故障的那条链路上，监控图上看起来像是别的地方坏了。

### 3. 区域自治：每个区域是一个独立网络单元

区域内自己管自己（本地业务在本地闭环），区域间才需要跨区通信。好处是故障可以被限制在区域内；坏处是**跨区域故障会跨越多个自治域**，定位范围一下子扩大 8 倍。

### 4. 单区域内部：五层分层结构

文中罗列了 4 类设备，从下往上按业务流量经过的顺序：

```text
        ┌──────────────────────────────┐
        │  traffic-vm  service-vm ×3   │  ← 业务层（产生流量 / 提供服务）
        │  monitor-vm                  │     监控层（只采集，不产生业务流量）
        └───────────────┬──────────────┘
                        │
                ┌───────┴────────┐
                │  接入交换机 ×4  │  ← 接入层（VM 挂这里）
                └───────┬────────┘
                        │
                ┌───────┴────────┐
                │    防火墙 ×1    │  ← 安全层（策略过滤，可能拦流量）
                └───────┬────────┘
                        │
                ┌───────┴────────┐
                │  核心路由器 ×2  │  ← 核心层（cr-1/cr-2）
                └───────┬────────┘
                        │
                ┌───────┴────────┐
                │  边界路由器 ×2  │  ← 边界层（br-1/br-2，出口接其他区域）
                └────────────────┘
```

流量路径：`VM → 接入交换机 → 防火墙 → 核心路由器 → 边界路由器 → 出区域`。
**这条链路就是"全栈观测"的意思**：任意一跳出问题，都能在这一跳上观测到异常，不用猜。

> **两处对不上，需注意（我已在 comp.md 第 20 行记过）**：
> - 原文说"4 台路由器、4 台交换机、1 台防火墙、**6 台业务虚拟机**"，但官方 `node_id` 枚举只有 10 个网元，**完全没有交换机**，虚拟机是 `traffic-vm ×1 + service-vm ×3 + monitor-vm ×1 = 5 台`。
> - 所以做题时**以枚举表为准**（报名方明确要求只能用枚举值），交换机大概率不在根因候选范围内。

### 5. 三类特殊 VM

| 名称 | 干什么 | 对数据的影响 |
| --- | --- | --- |
| `traffic-vm` | **主动**发包，模拟用户访问业务 | 它的运行状态和访问结果 → **Flow 指标**（能不能访问通、延迟多少） |
| `service-vm-1/2/3` | 真正提供业务服务，是被访问方 | 它们的 Metrics（CPU/内存/磁盘）是**服务级故障**的直接证据 |
| `monitor-vm` | 只做监控采集、聚合、入库 | **赛题明确说明：monitor-vm 和 probe-vm 不在分析范围内**，永远不要提交它当根因 |

### 6. Flow 指标 vs NetFlow：两个不同的东西，别搞混

- **Flow 指标**：从 `traffic-vm` 的**主动探测行为**得到，是**端到端**视角——"我能不能访问通对端服务"。类似拨测。
- **NetFlow**：路由器上的导出组件（FRR 里的 `netflow` 插件）把**实际转发过的流记录**吐出来，是**设备级**视角——"这台路由器转发了哪些五元组、多少字节、什么时刻"。

两者互补：端到端说"坏了"，NetFlow 说"坏在哪个设备、哪条路径上"。这正是赛题让你把网络流数据也用上的原因。

### 7. 五类故障，一句话对照

| 大类 | 大白话 | 典型表现 |
| --- | --- | --- |
| **link（链路级）** | 线有问题：丢包、延迟、抖动、断开 | 时延指标飙升、重传、吞吐下降；NetFlow 看到流量骤降 |
| **firewall（防火墙级）** | 安全设备出问题：策略错、会话满、转发异常 | 流量在防火墙处"凭空消失"，但链路本身正常 |
| **routing（路由级）** | 路径选错了：路由震荡、下一跳错、绕行 | FRR 日志刷屏、路径突变；**异常出现在绕行后的新路径上** |
| **resource（资源级）** | 设备自己扛不住了：CPU/内存/磁盘打满 | 该网元自身的 Metrics 明显越界，是五类里**最好识别**的 |
| **service（服务级）** | 业务程序出问题：进程挂、响应慢、返回错误 | service-vm 的 Metrics + 访问失败率上升，网络设备指标却正常 |

**归类逻辑链**：先看"是一个网元自己指标炸了（resource）"，还是"网络通但业务不通（service）"，还是"网络本身不通/慢（link / firewall / routing）"；再用 **FRR 日志有没有刷屏**区分 routing，用 **流量在哪个位置开始丢** 区分 firewall 和 link。

## 三、和解题的关系（三行总结）

1. 三类数据各管一段：**Metrics 管"谁自己病了"**，**Logs 管"路由怎么了"**，**Flow/NetFlow 管"数据实际走到哪儿了"**。
2. 最大的坑是**故障传播和路径绕行**：受害网元 $\neq$ 故障网元。不要看到哪个指标最炸就填哪个。
3. 交付时记得：**候选必须满 5 个且不能重复**（重复整条判 0），大类枚举填 `routing` 而不是 `route`。
